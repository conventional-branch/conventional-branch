# Conventional Branch 1.0.0

## Краткое описание

Conventional Branch относится к структурированному и стандартизированному соглашению о наименовании веток Git, которое направлено на то, чтобы сделать ветки более читаемыми и действенными. Мы предложили некоторые префиксы веток, которые вы можете использовать, но вы также можете указать собственное соглашение о наименовании. Последовательное соглашение о наименовании упрощает идентификацию веток по типу.

### Ключевые моменты

1. **Названия веток, ориентированные на цель**: Каждое название ветки четко указывает на ее назначение, что позволяет всем разработчикам легко понять, для чего предназначена ветка.
2. **Интеграция с CI/CD**: Использование согласованных имен веток может помочь автоматизированным системам (например, конвейерам непрерывной интеграции/непрерывного развертывания) запускать определенные действия на основе типа ветки (например, автоматическое развертывание из веток релиза).
3. **Командное сотрудничество**: Это способствует сотрудничеству в командах, делая назначение ветки явным, уменьшая недопонимание и упрощая переключение между задачами без путаницы.

## Спецификация

### Префиксы именования веток

Спецификация веток поддерживает следующие префиксы и должна быть структурирована как:

---

```
<тип>/<описание>
```

- **`main`**: Основная ветка разработки (например, `main`, `master`, или `develop`)
- **`feature/`** (или **`feat/`**): Для новых функций (например, `feature/add-login-page`, `feat/add-login-page`)
- **`bugfix/`** (или **`fix/`**): Для исправления ошибок (например, `bugfix/fix-header-bug`, `fix/header-bug`)
- **`hotfix/`**: Для срочных исправлений (например, `hotfix/security-patch`)
- **`release/`**: Для веток, готовящих релиз (например, `release/v1.2.0`)
- **`chore/`**: Для задач, не связанных с кодом, таких как обновления зависимостей, документации (например, `chore/update-dependencies`)

---

### Основные правила

1. **Используйте строчные буквы, цифры, дефисы и точки**: Всегда используйте строчные буквы (`a-z`), цифры (`0-9`) и дефисы (`-`) для разделения слов. Избегайте специальных символов, подчеркиваний или пробелов. Для веток релиза в описании могут использоваться точки (`.`) для представления номеров версий (например, `release/v1.2.0`).
2. **Никаких последовательных, начальных или завершающих дефисов или точек**: Убедитесь, что дефисы и точки не появляются последовательно (например, `feature/new--login`, `release/v1.-2.0`), а также в начале или конце описания (например, `feature/-new-login`, `release/v1.2.0.`).
3. **Сохраняйте ясность и краткость**: Название ветки должно быть описательным, но кратким, четко указывающим на цель работы.
4. **Включайте номера тикетов**: Если применимо, включайте номер тикета из вашего инструмента управления проектами для упрощения отслеживания. Например, для тикета `issue-123` название ветки может быть `feature/issue-123-new-login`.

## Заключение

- **Четкая коммуникация**: Одно только название ветки обеспечивает четкое понимание цели изменения кода.
- **Удобство для автоматизации**: Легко интегрируется в процессы автоматизации (например, различные рабочие процессы для `feature`, `release` и т.д.).
- **Масштабируемость**: Хорошо работает в больших командах, где много разработчиков одновременно работают над разными задачами.

В заключение, conventional branch разработан для улучшения организации проекта, коммуникации и автоматизации в рабочих процессах Git.

## FAQ

### Какие инструменты можно использовать для автоматического определения того, что член команды не соответствует этой спецификации?

Вы можете использовать [commit-check](https://github.com/commit-check/commit-check) для проверки спецификации веток или [commit-check-action](https://github.com/commit-check/commit-check-action), если ваш код размещен на GitHub.
